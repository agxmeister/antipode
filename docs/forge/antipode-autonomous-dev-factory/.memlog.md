---
idea: Antipode: autonomous software development factory. Input: a problem. Spawns configurable independent agents working on pieces of the same problem in a shared workspace. User talks to it via web UI or Telegram; gets progress reports and intermediate/final demos; can request corrections. Extensible via skills and MCPs per agent role. SDD-framework friendly.
goal: Pressure-test the concept and harden it into something actionable (assumed; to be confirmed)
status: complete
updated: 2026-10-31T21:45
---

- (decision) Split into upstream (idea forming) and downstream (implementation). MVP focuses on downstream only; upstream later.
- (assumption) Downstream input is a set of tasks, some parallelizable, some needing synchronization. Each task is developed, tested, accepted.
- (direction) Each agent = a separate Claude instance (later Codex etc.) in a Docker container on one or several VMs. Project workspace = one separate container holding all project files, shared by all agents simultaneously.
- (direction) Dev rollout on Podman locally; production on a real cluster (AWS/DO/Solus) or bare metal on-prem.
- (note) Differentiation question (what beats Devin/Codex/agent teams) not answered yet; user moved to architecture.
- (lock) Agents do NOT edit the same tree simultaneously. Each agent works in its own working copy / feature branch; shared workspace means shared repo and visibility, not shared mutation. Dependent tasks synchronize via merge.
- (direction) CI/CD must run on all changes as frequently as possible (every agent branch, not just main).
- (lock) Every agent branch gets a deployed preview environment; the preview is the intermediate demo the user sees. Acceptance is human, per task, from the preview. After human acceptance: merge to main and deploy to prod.
- (crack) Human acceptance per task makes review throughput the real bottleneck of the autonomous factory; design must minimize review cost. Not yet addressed.
- (lock) First user is the author. Reviewer is exactly one person: the project owner. Single-tenant MVP.
- (lock) Review means assessing the user-facing RESULT (open a link on phone or laptop, look at the running preview), not reading code or diffs. Minimum text, maximum visualization. Review must be cheap, not a big deal.
- (direction) Later: delegate review to a specialized reviewer agent.
- (lock) Evidence artifact is a first-class object: every task must end with agent-produced evidence before it becomes reviewable. UI tasks: before/after screenshots or recording of the preview. Backend/data tasks: measurable proofs (record counts before/after, checksums, request/response, named test cases). Criterion: whatever lets the owner be confident in one glance.
- (decision) Differentiation: Antipode's product is the acceptance surface (preview + evidence + one-tap accept/correct from phone), not the agents. Agents, containers, branches, CI are plumbing.
- (lock) Task contract: tasks enter as structured specs with acceptance criteria (plus required evidence, dependencies). This is Antipode's input API and what SDD-friendly means: it consumes stories, does not invent them.
- (lock) Intake agent: if a task lacks criteria, an intake agent asks the owner for them (may use SDD skills to elicit). No task starts without acceptance criteria.
- (lock) Multiple agents per task with separated roles: e.g. one implements, another validates on the feature branch. Worker does not grade its own work.
- (decision) No global orchestrator. Specialized agents per stage, each with its own context derived from a common shared ground (task record + repo).
- (crack) Unclear whether 'no global orchestrator' rejects only an orchestrator AGENT or also a deterministic coordinator. Without any coordinator: who advances stages, detects done, retries, kills stuck agents?
- (lock) Coordination: a non-intelligent coordinator holds task state, fires stage triggers, handles timeouts/retries. No central LLM reasoning about the whole project. Shared ground = task record + repo. Each stage agent starts fresh with its own context built from the shared ground and its role config.
- (direction) At decision points (e.g. after validation with non-critical findings), the coordinator may invoke a short-lived 'triage' agent in a clean context to decide the next stage: re-run implementer, or park findings in a deferred-work ledger (parking lot). Intelligence is a stage, not the coordinator.
- (lock) Correction = feedback on the existing task, same branch. No new intake, original criteria still apply plus owner note. Task returns to implementer with note + previous evidence in context; validator re-runs; evidence regenerated, report leads with diff vs what owner already saw. Owner note is free text; at most one clarifying question.
- (assumption) Every task has an iteration budget (implement/validate/triage laps). When spent, task goes to owner as 'stuck, here is why'. Parking lot (deferred findings) is shown at review so owner accepts knowingly.
- (lock) Dependent tasks start only when their dependencies are merged to main. No stacked branches in MVP. Accept does not merge: coordinator rebases on main, re-runs validator + CI, then merges and deploys to prod. Rebase conflict or failed validation returns the task to the implementer; owner gets a new preview only if the visible result changed. Every merge deploys to prod.
- (lock) MVP IN: structured task contract file in repo; coordinator with persisted state, triggers, timeouts, iteration budget; Claude-only roles each in a fresh container (intake, implementer, validator, evidence producer, triage) defined as config (instructions, skills, MCPs); branch per task; CI on every push; preview container per branch on one box; evidence report + preview link + accept/request-changes via Telegram; accept -> rebase, revalidate, merge, deploy to prod; Podman on one machine.
- (kill) Cut from MVP (phase two): web UI, multi-vendor agents (Codex etc.), cluster/cloud deployment, automated reviewer agent, upstream idea-forming.
- (decision) Owner kept intake agent and triage agent (with parking lot) in MVP despite cut proposal.
- (lock) Agent containers are ephemeral (created per stage, destroyed when the artifact is written); nothing LLM-shaped runs while a task waits for the owner. Preview containers are the only long-lived cost; they sleep on inactivity and wake on request.
- (lock) Billing in MVP: Claude Code subscription sessions, throttled by per-task iteration budget. API tokens are a phase-two switch.
- (lock) Cost tracking is essential: owner can see subscription spend with per-task and per-stage detail (tokens, wall time), shown in the evidence report and on demand.
- (crack) Claude subscription spend is not metered in money; only tokens, session time, and rate-limit window usage are observable. Cost tracking must be built on what the harness exposes, and the mapping to 'subscription spend' is approximate. Needs verification during design.
- (lock) Project recipe checked into the repo (build, preview run, CI, prod deploy, seed data, preview secrets). Antipode consumes it, never invents it; owner writes it in MVP. Each preview has its own ephemeral DB seeded from a fixture; no prod snapshots. External services via sandbox creds or stubs declared by the project.
- (lock) Antipode ENFORCES demo-first: a project must have a working preview/demo environment before feature tasks start. The first task of any new project is creating that environment (recipe + preview). Fallback to tests-plus-screenshots evidence exists only as a degraded mode, not a way to skip the recipe.
